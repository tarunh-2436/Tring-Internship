# Overview

The Feedback API is a cloud-native feedback management application designed to collect, manage, and administer user feedback while supporting optional file attachments.

The system follows a fully serverless architecture and is built entirely on AWS services. Rather than uploading attachments through the backend, clients upload files directly to Amazon S3 using presigned URLs generated by AWS Lambda. This approach minimizes backend processing, reduces bandwidth consumption, and improves scalability.

To maintain consistency between Amazon S3 and Amazon DynamoDB, feedback creation and editing follow a two-phase transaction model:

```text
Initialize Request

↓

Generate Presigned URLs

↓

Upload Attachments

↓

Verify Uploads

↓

Persist Feedback
```

Feedback is stored only after every expected attachment has been successfully verified. If verification fails, the backend performs automatic rollback by removing newly uploaded files and preventing inconsistent records from being written to the database.

The entire infrastructure is provisioned through Terraform, allowing the application to be recreated from source with minimal manual configuration.

# System Architecture

The Feedback API follows a layered serverless architecture in which each AWS service is responsible for a single aspect of the application. The frontend communicates with the backend through Amazon API Gateway, while business logic is implemented in AWS Lambda. Feedback metadata is stored in Amazon DynamoDB, and attachments are stored separately in Amazon S3.

# Database Design

The application uses **Amazon DynamoDB** as its primary datastore for feedback records. DynamoDB was selected because it is a fully managed serverless database that provides low-latency access, automatic scaling, and seamless integration with AWS Lambda.

The database stores **feedback metadata only**. Attachment files are stored separately in Amazon S3.

---

# Data Model

Each feedback submission is represented by a single DynamoDB item.

| Attribute     | Description                             |
| ------------- | --------------------------------------- |
| `ownerId`     | Unique identifier of the feedback owner |
| `feedbackId`  | Unique identifier of the feedback       |
| `ownerType`   | User category (`USER` or `ANONYMOUS`)   |
| `title`       | Feedback title                          |
| `content`     | Feedback content                        |
| `attachments` | List of attachment metadata             |
| `status`      | Current feedback status                 |
| `createdAt`   | Creation timestamp                      |
| `lastUpdated` | Last modification timestamp             |
| `entityType`  | Entity discriminator                    |

A typical record is structured as follows:

```json
{
    "ownerId": "...",
    "feedbackId": "...",
    "ownerType": "USER",
    "title": "...",
    "content": "...",
    "attachments": [
        {
            "filename": "example.pdf",
            "contentType": "application/pdf"
        }
    ],
    "status": "ACTIVE",
    "createdAt": "...",
    "lastUpdated": "...",
    "entityType": "FEEDBACK"
}
```

---

# Primary Key Design

The table uses a composite primary key.

| Key           | Attribute    |
| ------------- | ------------ |
| Partition Key | `ownerId`    |
| Sort Key      | `feedbackId` |

```text
(ownerId, feedbackId)
```

This design guarantees uniqueness while allowing all feedback belonging to a specific user to be retrieved efficiently.

Example:

```text
ownerId

├── feedback1
├── feedback2
└── feedback3
```

---

# Attachment Metadata

The database intentionally stores **only attachment metadata**, not the attachment contents.

Example:

```json
[
    {
        "filename": "report.pdf",
        "contentType": "application/pdf"
    },
    {
        "filename": "image.png",
        "contentType": "image/png"
    }
]
```

The corresponding files are stored in Amazon S3.

Separating metadata from binary data provides several advantages:

* Smaller database items
* Lower storage costs
* Faster queries
* Independent scaling of storage
* Simplified attachment management

---

# Attachment Storage Layout

Attachments are organized in Amazon S3 using the following hierarchy:

```text
uploads/

    ownerId/

        feedbackId/

            attachment1

            attachment2

            attachment3
```

Example:

```text
uploads/

    d4482428-f0...

        8d11d2f4...

            screenshot.png

            report.pdf
```

This structure makes it straightforward to locate and remove all files associated with a feedback record.

---

# Status Management

Each feedback record includes a `status` field.

Current values:

| Status   | Description            |
| -------- | ---------------------- |
| `ACTIVE` | Active feedback record |

The field is designed to support future extensions such as:

* `ARCHIVED`
* `DELETED`

without requiring changes to the table schema.

---

# Timestamp Strategy

Each record stores two timestamps.

| Field         | Purpose                          |
| ------------- | -------------------------------- |
| `createdAt`   | Time of initial creation         |
| `lastUpdated` | Time of most recent modification |

Both values are stored in ISO 8601 UTC format.

Example:

```text
2026-06-12T14:35:18.624Z
```

This format is:

* Human-readable
* Timezone independent
* Lexicographically sortable

---

# Owner Types

The application supports two owner categories.

| Owner Type  | Description              |
| ----------- | ------------------------ |
| `USER`      | Authenticated submission |
| `ANONYMOUS` | Anonymous submission     |

Authenticated feedback uses the user's Cognito identifier as the `ownerId`, while anonymous feedback is assigned a randomly generated UUID.

This allows both submission types to share a common storage model.

---

# Query Patterns

The database schema was designed around the application's primary access patterns.

| Operation                    | Query Pattern          |
| ---------------------------- | ---------------------- |
| Retrieve user's feedback     | `ownerId`              |
| Retrieve a specific feedback | `ownerId + feedbackId` |
| Update feedback              | `ownerId + feedbackId` |
| Delete feedback              | `ownerId + feedbackId` |

To support administrative operations, the application also uses a **Global Secondary Index (GSI)** that enables querying feedback independently of `ownerId`, allowing administrators to retrieve all feedback efficiently without relying on full table scans.

---

> [!NOTE]
>
> DynamoDB stores only the metadata required to describe a feedback record. Attachment files themselves are stored separately in Amazon S3, allowing each storage system to be optimized for its intended purpose.

# Create Feedback

Feedback creation is implemented as a two-step process consisting of an initialization request followed by a completion request.

## Step 1

### POST `/feedback/init`

Initializes feedback creation and generates upload URLs for any requested attachments.

### Request

```json
{
    "attachments": [
        {
            "filename": "image.png",
            "contentType": "image/png"
        }
    ]
}
```

### Response

```json
{
    "feedbackId": "...",
    "uploads": [
        {
            "filename": "image.png",
            "uploadUrl": "...",
            "contentType": "image/png"
        }
    ]
}
```

No feedback record is created during this step.

---

## Step 2

### POST `/feedback/complete`

Completes feedback creation after attachment uploads.

### Request

```json
{
    "feedbackId": "...",
    "title": "...",
    "content": "...",
    "attachments": [
        {
            "filename": "image.png",
            "contentType": "image/png"
        }
    ]
}
```

### Success Response

```json
{
    "message": "Feedback stored successfully",
    "feedbackId": "..."
}
```

# Authentication & Authorization

The application uses **Amazon Cognito** as its identity provider for user authentication and implements **role-based authorization** for protected operations.

Authentication is handled using the **OAuth 2.0 Authorization Code Flow**, while authorization decisions are enforced by the backend using information extracted from JWT tokens.

The system supports three categories of users:

* Guest users
* Authenticated users
* Administrators

---

# Authentication Flow

Users authenticate through the Amazon Cognito Hosted UI.

```text
User

↓

Login

↓

Amazon Cognito Hosted UI

↓

Authentication

↓

Authorization Code

↓

Frontend

↓

JWT Tokens

↓

Authenticated Session
```

The application never handles user credentials directly. Authentication is delegated entirely to Amazon Cognito.

---

# JWT Authentication

After a successful login, the frontend obtains OAuth tokens from Cognito and includes the access token in protected API requests.

```http
Authorization: Bearer <access_token>
```

The backend extracts user information from the token before executing any protected operation.

---

# User Roles

| Role  | Description                 |
| ----- | --------------------------- |
| Guest | Not authenticated           |
| User  | Authenticated user          |
| Admin | Authenticated administrator |

Guest users may submit anonymous feedback.

Authenticated users may manage their own feedback.

Administrators have read-only access to all feedback records.

---

# Permission Matrix

| Operation                     | Guest |     User     | Admin |
| ----------------------------- | :---: | :----------: | :---: |
| Submit Anonymous Feedback     |   ✅   |       ✅      |   ✅   |
| Submit Authenticated Feedback |   ❌   |       ✅      |   ✅   |
| View Own Feedback             |   ❌   |       ✅      |   ✅   |
| View All Feedback             |   ❌   |       ❌      |   ✅   |
| View Individual Feedback      |   ❌   | ✅ (Own Only) |   ✅   |
| Edit Feedback                 |   ❌   | ✅ (Own Only) |   ❌   |
| Delete Feedback               |   ❌   | ✅ (Own Only) |   ❌   |
| Download Feedback             |   ❌   | ✅ (Own Only) |   ✅   |

---

# Authorization Model

Ownership is determined by the backend rather than by client-supplied data.

For protected operations, the backend:

1. Extracts the authenticated user's identity from the JWT.
2. Determines whether the caller is an administrator.
3. Verifies that the requested resource belongs to the caller when required.
4. Executes the operation only if authorization succeeds.

Unauthorized requests receive an HTTP **403 Forbidden** response.

# Frontend Configuration

Authentication parameters are generated automatically during deployment and exposed through the frontend configuration file.

Example:

```javascript
window.APP_CONFIG = {

    API_URL: "...",

    COGNITO_DOMAIN: "...",

    CLIENT_ID: "...",

    REDIRECT_URI: "..."

};
```

This configuration is generated by Terraform, eliminating manual updates when infrastructure changes.

---

> [!IMPORTANT]
>
> Authentication determines **who** the user is, while authorization determines **what** the user is allowed to do. The backend validates both before executing protected operations.

> [!NOTE]
>
> The Cognito Hosted UI domain and Client ID are public OAuth configuration values and are intentionally available to the frontend. Sensitive credentials such as AWS access keys or Cognito client secrets are never exposed to the client application.

# Deployment

The Feedback API is designed to be deployed entirely using **Terraform**. All required AWS resources are provisioned as Infrastructure as Code, eliminating the need for manual configuration through the AWS Management Console.

## Prerequisites

Before deployment, ensure the following tools are installed:

| Tool        | Purpose                     |
| ----------- | --------------------------- |
| Terraform   | Infrastructure provisioning |
| AWS CLI     | AWS authentication          |
| Python 3    | Lambda development          |
| Zip Utility | Lambda packaging            |

An AWS account with sufficient permissions is also required.

---

## Infrastructure Provisioned

Terraform automatically provisions:

* Amazon API Gateway
* AWS Lambda
* Amazon DynamoDB
* Amazon S3
* Amazon CloudFront
* Amazon Cognito
* AWS IAM Roles and Policies

---

## Deployment Steps

Initialize Terraform:

```bash
terraform init
```

Review the execution plan:

```bash
terraform plan
```

Deploy the infrastructure:

```bash
terraform apply
```

If the Lambda source code changes, package the function before deployment:

```bash
cd lambda

zip -r lambda.zip .
```

and then execute:

```bash
terraform apply
```

# Design Decisions

The implementation is guided by the following architectural principles:

* Fully serverless architecture
* Infrastructure as Code using Terraform
* Separation of frontend, backend, and infrastructure
* Direct browser-to-S3 attachment uploads
* Two-phase transactional feedback creation and editing
* Independent storage of metadata and binary files
* Backend-enforced authorization
* Automatic cleanup of orphaned attachments
* Modular and maintainable project organization

These decisions prioritize consistency, scalability, and simplicity while minimizing operational overhead.
